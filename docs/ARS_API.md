# Ars Nouveau integration verified against 4.12.7

The addon does not patch, modify, or redistribute Ars Nouveau source. Its API calls were checked against the installed `ars_nouveau-1.20.1-4.12.7-all.jar`, the remapped development jar, and the official source publication.

- Official repository commit: [`2c74064bc753600d9b6600f102f8163e2d6764dd`](https://github.com/baileyholl/Ars-Nouveau/tree/2c74064bc753600d9b6600f102f8163e2d6764dd), branch `1.20`, June 23, 2025. `build.gradle` declares version `4.12.7` and Java 17; `gradle.properties` declares Minecraft `1.20.1`.
- Published Forge release: [Ars Nouveau 4.12.7](https://modrinth.com/mod/ars-nouveau/version/Hw2aD01e), Minecraft 1.20.1. The installed release is the implementation target, rather than a guessed current-version API.
- Official Maven coordinates: `com.hollingsworth.ars_nouveau:ars_nouveau-1.20.1:4.12.7.264`, repository `https://maven.blamejared.com`. The build-number suffix is required on that Maven; `4.12.7` alone is not a published Maven version there.
- [Official source jar](https://maven.blamejared.com/com/hollingsworth/ars_nouveau/ars_nouveau-1.20.1/4.12.7.264/ars_nouveau-1.20.1-4.12.7.264-sources.jar). The brazier, base ritual, and ritual registry files were compared with the pinned repository commit and match.

## Actual ritual API and item behavior

[`RitualRegistry`](https://github.com/baileyholl/Ars-Nouveau/blob/2c74064bc753600d9b6600f102f8163e2d6764dd/src/main/java/com/hollingsworth/arsnouveau/api/registry/RitualRegistry.java) exposes `registerRitual(AbstractRitual)` and instantiates each ritual with a public no-argument constructor. `ConstructionRitual` supplies that constructor and a namespaced ID.

[`ItemsRegistry.onItemRegistry`](https://github.com/baileyholl/Ars-Nouveau/blob/2c74064bc753600d9b6600f102f8163e2d6764dd/src/main/java/com/hollingsworth/arsnouveau/setup/registry/ItemsRegistry.java#L241) automatically creates a normal Ars tablet for every ritual present during the item registration event. This addon registers its ritual during common setup, after item registration, so it adds only the two requested items.

[`RitualTablet.useOn`](https://github.com/baileyholl/Ars-Nouveau/blob/2c74064bc753600d9b6600f102f8163e2d6764dd/src/main/java/com/hollingsworth/arsnouveau/common/items/RitualTablet.java#L33) calls `setRitual` and consumes the held stack without preserving its NBT. Consequently the addon's items extend Minecraft `Item`, not the default Ars `RitualTablet`. A validated ordinary right click on a brazier calls the addon's server handler, which only installs the custom ritual and pays the loading costs, preserving the tablet by default. Sneak right click retains its selection-point meaning.

Activation uses the actual [`RitualBrazierBlock.use`](https://github.com/baileyholl/Ars-Nouveau/blob/2c74064bc753600d9b6600f102f8163e2d6764dd/src/main/java/com/hollingsworth/arsnouveau/common/block/RitualBrazierBlock.java#L68) empty-main-hand path, calling `startRitual(player)` and our `canStart/onStart` hooks. The owner, reach, dimension, permissions and redstone state are validated on the server. The native tile handles ignition, fire particles, casting sound and final extinguishing. Ars has no universal warmup: `RitualAwakening.tick` counts seconds before resolving, and `RitualWildenSummoning.tick` waits eight progress steps. Following this subclass pattern, construction waits `ritualWarmupTicks` (100 by default) after activation before placing its first batch. The job persists its activation flag and remaining warmup; the ritual's native context preserves the installed-but-unstarted state. Old jobs without these fields remain resumable as already activated jobs without a new warmup or fee.

The two addon item JSON models inherit `ars_nouveau:item/ritual_restoration` and `ars_nouveau:item/ritual_binding`. Both model names, generated parent and textures were verified inside the installed 4.12.7 JAR. This reuses the original tablet silhouette and sprite rendering without copying or editing upstream assets; resource-pack overrides are honored. These are shared native appearances, not new unique glyph artwork.

[`RitualBrazierTile`](https://github.com/baileyholl/Ars-Nouveau/blob/2c74064bc753600d9b6600f102f8163e2d6764dd/src/main/java/com/hollingsworth/arsnouveau/common/block/tile/RitualBrazierTile.java) exposes `setRitual(ResourceLocation)`, `startRitual(Player)`, public `ritual`, and `updateBlock()` inherited from `ModdedTile`. There is no generic fuel slot or stored core `ItemStack`. Ars ritual augments are consumed through `canConsumeItem` / `onItemConsumed`; this addon instead offers explicitly configured startup fuel from the triggering player's inventory.

[`RitualBrazierBlock.playerWillDestroy`](https://github.com/baileyholl/Ars-Nouveau/blob/2c74064bc753600d9b6600f102f8163e2d6764dd/src/main/java/com/hollingsworth/arsnouveau/common/block/RitualBrazierBlock.java#L98) drops a fresh ordinary ritual tablet for an unstarted, unfinished ritual. Our `onDestroy` first marks the ritual finished and removes its job; failed installation is rolled back. The addon deliberately does not add its items to Ars's ritual-item map, which also avoids its automatic dispenser behavior consuming a data-bearing tablet without transferring data.

## Source, job persistence, and effects

[`SourceUtil.canTakeSource`](https://github.com/baileyholl/Ars-Nouveau/blob/2c74064bc753600d9b6600f102f8163e2d6764dd/src/main/java/com/hollingsworth/arsnouveau/api/util/SourceUtil.java#L34) discovers source jars and registered special source providers. The addon scans once per construction batch, deduplicates underlying `ISourceTile` instances, and calls their verified `getSource` / `removeSource` API only after ensuring the full next-block cost is available. This allows a cost to span jars. Without sufficient Source the cursor does not advance. Startup Source is checked before any inventory consumption. The radius is six blocks, matching the native brazier.

The native brazier automatically drains Source only when `consumesSource()` and `needsSourceNow()` are true. This addon leaves that mechanism disabled and performs its own per-block charging to ensure costs correspond to the construction cursor, including after a restart. There is no second automatic Source charge.

[`AbstractRitual`](https://github.com/baileyholl/Ars-Nouveau/blob/2c74064bc753600d9b6600f102f8163e2d6764dd/src/main/java/com/hollingsworth/arsnouveau/api/ritual/AbstractRitual.java) provides `onStart(Player)`, `tryTick(RitualBrazierTile)`, `tick`, `write`, `read`, `onDestroy`, and `onEnd`. The brazier may pass a relay to `tryTick`; this implementation resolves the job's original brazier and never moves the target anchor or charging location with a relay.

`ModdedTile.getUpdateTag()` calls `saveAdditional()`, which calls the ritual's `write`. Therefore storing a complete structure inside the ritual would also put it into an ordinary vanilla block-entity network packet. The addon saves the structure and placement bitmap in overworld `SavedData` named `arsstructura_construction_jobs`; the ritual stores only a UUID and bounded progress/context. Saving/loading the world retains job progress. Offline owners and unloaded chunks pause jobs. Breaking the brazier cancels them, and periodic cleanup removes jobs displaced by another ritual without loading chunks.

Real Ars effects used here are [`ParticleUtil.spawnFollowProjectile` and `spawnTouchPacket`](https://github.com/baileyholl/Ars-Nouveau/blob/2c74064bc753600d9b6600f102f8163e2d6764dd/src/main/java/com/hollingsworth/arsnouveau/client/particle/ParticleUtil.java) with `ParticleColor`, plus `SoundRegistry.APPARATUS_FINISH`. The brazier itself plays its normal ignition, casting and extinguishing sounds. `spawnTouchPacket` delegates to Ars [`Networking.sendToNearby`](https://github.com/baileyholl/Ars-Nouveau/blob/2c74064bc753600d9b6600f102f8163e2d6764dd/src/main/java/com/hollingsworth/arsnouveau/common/network/Networking.java#L229), which sends registered Ars effect packets to tracking players within 64 blocks. Custom tablet requests and structure transfers use the addon's own Forge channel.

## Placement and rendering boundary

Actual placement only runs on `ServerLevel`, with the online owner, matching dimension, loaded destination chunk, world-border/build-height validation, replaceability policy, blacklists, and protection events. Existing block entities and unbreakable blocks are never overwritten, even with force replacement. A Forge `BlockEvent.EntityPlaceEvent` subclass exposes the proposed state while its snapshot preserves the old state, allowing cancellation before mutation. Forced replacement additionally posts `BlockEvent.BreakEvent`. Integration with protection mods still requires testing against the specific server pack because mods can impose rules outside Forge's standard events.

All states are placed before the finishing phase restores approved block-entity NBT at relocated absolute coordinates and notifies neighbors. Protection is checked again for delayed block-entity restoration. If a player or automation has already put items into a newly created container, its restoration is skipped and reported, preserving the new contents. No entities are copied. Default data sanitization removes inventories and active text actions; administrators may explicitly configure allowed block entity types and inventory copying.

Ghost previews use the addon's client renderer and Forge `RenderLevelStageEvent`; the upstream ghostweave block-entity renderer is not a ready-made structure-preview API. Previews must never call world placement or the ritual handler. Client rendering, local files, and Screens remain separate from the dedicated-server entry points.

Selection outlines use a separate `AFTER_PARTICLES` listener and the server-synchronized item summary. Corner 1 is cyan, corner 2 is orange, and the inclusive selection bounds are pale gold. A faint pass without depth testing and a brighter depth-tested pass use the vanilla line shader with the particles output target and color-only writes. No world data changes or structure decompression occur during line rendering. Item selection, dimension, world state, GUI visibility, distance and frustum tests determine visibility without retaining stale selection caches.

## Creative inventory round trips

Large structure bytes are excluded from vanilla ItemStack share tags and travel only through the bounded custom transfer channel. Creative inventory packets can return these metadata-only stacks to the server. Before changing an item's structure, the server archives the validated compressed payload in overworld `SavedData` named `arsstructura_tablet_structures`, keyed by its SHA-256 content hash. The small key survives the creative round trip; the server restores the hidden payload before gameplay or on an inventory tick, without changing the visible revision or accepting structure bytes from that packet.

The archive deduplicates identical payloads and is bounded by `maxBackupBytes` (64 MiB default) and `maxBackupStructures` (8,192 default). A new save/import that would exceed either quota fails before changing the item; existing entries are not evicted. Archive loading checks key syntax, hashes, entry count, and compressed byte limits. Missing or corrupt backups do not crash inventory ticks. Complete item stacks still contain their own persistent structure bytes. Keep this SavedData file with world backups; deleting it or reducing its limits can prevent recovery of metadata-only creative copies. Normal complete stacks require no per-tick structure copying or decompression.
